## 3. Acımasız Eleştiri (ciddiyete göre)

**Kritik**
1. **`POST /dispatch-runs`'ta idempotency key yok.** `run_id = RQ job id` yalnızca worker'ın aynı run'ı iki kez işlememesini garantiler; istemci timeout sonrası POST'u retry ederse her çağrı yeni bir `DispatchRun` yaratır, iki run aynı pending havuzunu görüp yarışır. Stripe pattern'i: `Idempotency-Key` header, aynı key'e ilk sonucu dön, farklı parametre → hata, 24 saat sonra prune.
2. **Auth/authz sıfır.** Herkes her şeyi görüp değiştirebiliyor.
3. **Redis tek instance, SPOF.** Replika/Sentinel yok; düşerse enqueue ve worker durur. Prod pattern: 1 replika + 3 Sentinel (quorum). Portföy ölçeğinde bilinçli sınır olarak belgelenmeli.

**Orta**
4. **`/technicians`, `/jobs` pagination'sız** — her çağrı tüm tabloyu çeker. Cursor-based (keyset) standart.
5. **`dispatch_runs` hiç temizlenmiyor** — sınırsız büyür. Stripe idempotency key'lerini bile 24 saat sonra prune ediyor.
6. **Observability sıfır** — structured logging, metrics, tracing yok; worker'da bir run neden `failed` oldu, hangi correlation ID ile sorgulanacak bilinmiyor.
7. **Client polling, push yok** — tek yönlü durum için SSE, WebSocket'ten daha basit ve doğru.
8. **RQ/Redis'in Kafka'ya göre sınırları belgelenmemiş** — Redis job'ı kaybolursa run `queued`'da sonsuza kalır; worker restart'ında stuck-in-`running` senaryosu ele alınmamış.
9. **OpenAPI'de security scheme yok, API versioning yok** — frontend varken breaking change yönetimi belirsiz.
10. **Rate limiting yok** — Redis mevcut, token-bucket ucuz.

**Düşük**
11. **Audit trail / soft-delete yok** — tüm update'ler hard overwrite; "kim ne zaman değiştirdi" cevapsız.
12. **`assignments` JSONB vs ilişkisel tablo** — "teknisyene son 30 günde kaç iş atandı" JSONB parse gerektirir.
13. **Windows `SimpleWorker` fallback** — dev-only, CLAUDE.md'de doğru belgelenmiş; sorun değil.
14. **Tek dispatch stratejisi** — `Strategy` arayüzü yok; "hangi run hangi stratejiyle çalıştı" tutulmuyor. Şu ölçekte over-engineering olabilir.

## 4. Öncelikli Öneri Yol Haritası

**P0**
- Idempotency key on `POST /dispatch-runs` (ve diğer POST'lar). Postgres'te `idempotency_keys` tablosu, farklı parametre → hata, 24 saat prune. Domain'e sızmaz.
- Auth: API-key tabanlı FastAPI `Security` dependency (OpenAPI'de görünür). Tam OAuth2/JWT'ye henüz gerek yok.
- Redis SPOF'u belgele (README + CLAUDE.md); Sentinel şu an aşırı.

**P1**
- Cursor-based pagination (`/technicians`, `/jobs`).
- `dispatch_runs` TTL/arşivleme + stale run reconciliation.
- Minimal observability: structlog (JSON) + OpenTelemetry `FastAPIInstrumentor`, request-id/run-id korelasyonu.
- Polling yerine SSE (`/dispatch-runs/{id}/events`), plain `StreamingResponse`.

**P2**
- Rate limiting (Redis token-bucket).
- API versioning (`/v1`).
- Audit trail (timestamp'ler + append-only event satırları); soft-delete yalnızca DELETE endpoint'i gelirse.
- `assignments` JSONB → ilişkisel tablo, sorgulanabilirlik ihtiyacı doğarsa.
- Pluggable dispatch strategy, ikinci strateji gelirse.

## 5. "Bunu Yapma" Listesi

- **Kafka'ya şimdi geçme** — tek-worker senaryoda RQ + Postgres-source-of-truth outbox pattern'in özünü veriyor; Kafka over-engineering.
- **Multi-tenancy'yi şimdiden tasarlama** — gerçek ikinci tenant ihtiyacı doğmadan spekülatif karmaşıklık.
- **WebSocket'e SSE yerine gitme** — dispatch run durumu tek yönlü.
- **Netflix Dispatch'in plugin mimarisini taklit etme** — domain farklı, proje arşivli.
- **Timefold/OptaPlanner'a geçmeyi düşünme** — Faz 9 OR-Tools'a kilitli, Python domain kararıyla çelişir.
